# Process the Implementation Plan

The only front door for `todo/implementation-plan.md` when the user did not name a single phase. The file is a **derived projection**: processing it is not "pick a row and improvise", and it is not "tick the boxes".

This skill does not ship a section. It does not write a stamp. Writes stay serial, and the run this skill starts is the only writer on the tree: subagents it dispatches write only the paths its lead assigns them, inside that run.

## 0. Route

```bash
git status -sb
python3 scripts/todo-graph.py validate
python3 scripts/todo-graph.py query ready
```

| State | Do this |
| ----- | ------- |
| Another writer holds the tree | Stop and say so. Two writers on one tree is how a call ships without its interface. |
| Argument is `--audit` | Audit below, then stop. Do not start a run. |
| Argument is a phase (`0`, `Phase 0`) | That is `process-phase` for that phase only. It does not chain. |
| Empty argument, "the plan", "process the plan", or this file's path | Audit, then **start `process-phase` on the first phase with a ready row, in this same turn**. After that phase's closeout *or park*, pick the next ready phase. Repeat until no phase has a ready row. |

**An audit-only reply is a process defect.** Ending on the audit table while a ready phase exists is how a plan stalls while everyone agrees it is fine. Starting the phase is the next action, in the same turn.

## 1. Audit the whole plan

```bash
python3 scripts/todo-graph.py validate
python3 scripts/todo-graph.py plan --check
python3 scripts/todo-graph.py query ready
python3 scripts/todo-graph.py query blocked
python3 scripts/todo-graph.py query budget
```

The audit is these commands and the recorded lines, nothing more: the deep phase repair belongs to `process-phase` step 1. Fix every FATAL before talking about shipping. If `plan --check` is stale, run `plan --sync`, then re-check. **Never tick a box in `implementation-plan.md` by hand**: the boxes are a projection of the Implementation Order tables.

Record these lines **in the run's findings file**, not as the turn's last words:

1. Graph: fatal count.
2. Plan currency: the `--check` result.
3. Ready rows: count and first ref per phase.
4. Blocked rows: count and what blocks them.
5. Budget: sections and discovered sections per phase, discovered sections per run (provenance), and the backlog's entry count. Nothing is capped (operator decision 2026-09-27). A budget, origin, backlog, or release-gate FATAL (`backlog-dropped`, `release-backlog-review-missing`, `release-backlog-unreviewed`) is fixed like any other before shipping: restore a dropped entry or record the operator's approval, and run a release's backlog review before its stamp.
6. The phase being started, and why it is first.

If no phase has a ready row, every remaining `[ ]` row is blocked or runnable-elsewhere in this context. Report them and stop. That is a genuine halt, and it is the only one this skill has.

Ready means runnable-now in the current context: `query ready` splits runnable-now from runnable-elsewhere, and this skill offers only runnable-now rows. Elsewhere rows stay visible in the recorded lines, never offered, never started; re-run the query rather than trusting a previous list.

### Run guard

A run without a guard dies silently when the session stalls, so starting the first phase also starts the run guard, always. The guard has three parts, and they cover different failures. The writers map the abstract names onto their own tools: in Claude Code (`claude`), `CronCreate`/`CronList`/`CronDelete` are its schedule tools (cron `3-59/5 * * * *`, `Prompt: <canonical prompt>`), and the session id is `$CLAUDE_CODE_SESSION_ID`. In Muse (`muse`), they are the `muse.cron_create` / `muse.cron_list` / `muse.cron_delete` tools, and the session id is the Muse session id. In Antigravity (`agy`), `CronCreate` means calling the `schedule` tool (`CronExpression: "3-59/5 * * * *"`, `Prompt: <canonical prompt>`), `CronList` means `manage_task(Action="list")`, `CronDelete` means `manage_task(Action="kill", TaskId="<job id>")`, and the session id is this session's `Conversation ID` from `<user_information>`. In Codex (`codex`), the candidate session id is `$CODEX_THREAD_ID`. Before a Codex campaign, verify that the session's `git rev-parse --show-toplevel` resolves to this RasterFold checkout, `.codex/hooks.json` is trusted in `/hooks`, and a real native Stop event has the same `session_id` as that variable and continues the owner. Identify native in-session tools that create, list and cancel a recurring heartbeat targeting this same session. Record the tool names and the identity and continuation proof in the run file. In OpenCode (`opencode`), the session id is `$OPENCODE_SESSION_ID`; `CronCreate` is `python3 scripts/opencode-heartbeat.py create --session $OPENCODE_SESSION_ID --cron '3-59/5 * * * *' --prompt-file <scratch file holding the canonical prompt>` (it prints the job id), `CronList` is `python3 scripts/opencode-heartbeat.py list`, and `CronDelete` is `python3 scripts/opencode-heartbeat.py delete --job <job id>`; the plugin `.opencode/plugins/rasterfold-campaign/index.js` is both the Stop hook (on each turn end it runs `scripts/opencode-campaign-hook.py` and queues the guard's reason) and the heartbeat's delivery (it polls `opencode-heartbeat.py due` every 30 seconds and queues each due prompt into its idle session). Before an OpenCode campaign, prove the plugin is loaded in this session's server: create a probe job for this session with a cron that matches the next minute and a prompt naming the probe, read its `created=<UTC>` timestamp with `python3 scripts/opencode-heartbeat.py list`, end the turn saying it waits for the probe, and when the probe's prompt arrives as a new turn, delete the job, run `python3 scripts/opencode-campaign-hook.py --seen --session $OPENCODE_SESSION_ID --since <probe created_at>` to confirm that ending the probe turn reached the Stop-hook adapter (`seen <session> at <UTC>`), and record the probe job id, arrival time, and `seen` line in the run file. A probe that never arrives or a `--seen` check that exits non-zero means the plugin or its event subscription is not active (a service started before `.opencode/plugins/` existed loads it after `opencode reload`): no campaign starts. In GitHub Copilot CLI (`copilot`), any model including Auto is allowed (operator decision 2026-10-30: "remove the model pin"); the session id is `$COPILOT_AGENT_SESSION_ID`; `CronCreate` is the `manage_schedule` tool with `action: "create"`, `cron: "3-59/5 * * * *"` and `prompt: <canonical prompt>` (it returns the schedule id), `CronList` is `manage_schedule` with `action: "list"`, and `CronDelete` is `manage_schedule` with `action: "stop"` and `id: <schedule id>`. Copilot CLI loads the PascalCase `Stop` hook in `.claude/settings.json` (its VS Code compatible payload carries `session_id`, and it honours `{"decision": "block", "reason": ...}`), so it runs `campaign_guard.py stop-hook` with no adapter; its own runaway cap ends a turn after 8 consecutive blocks, above the guard's 3-block stall breaker. Before a Copilot campaign, prove both in this session with no other guard live: write a scratch run file `build/copilot-probe-run.md`, run `python3 scripts/campaign_guard.py acquire --session $COPILOT_AGENT_SESSION_ID --phase 0 --run-file build/copilot-probe-run.md --cron-id copilot-probe`, and end the turn; a native Stop event carrying this session id must block it and return the guard's `Campaign run is still open` reason as the next turn (with `query ready` printing at least one runnable row). Then append a column-0 `PARKED <UTC> run=<run id> probe` line to the scratch file, run `end --session $COPILOT_AGENT_SESSION_ID --reason park` and `cancel-confirmed --cron-id copilot-probe`, and delete the scratch file. Next create a probe schedule with `manage_schedule` (`interval: "1m"`, a prompt naming the probe), end the turn, and when the probe prompt arrives stop the schedule and confirm it gone with `action: "list"`. Record both proofs in the run file. If any capability is missing or unproven, stop without starting or acquiring a campaign; an external timer or the guard file alone is not a substitute. Below, `$CLAUDE_CODE_SESSION_ID` means this session's id in whichever harness runs it.

- **Stop hook** (`python3 scripts/campaign_guard.py stop-hook`, wired in `.claude/settings.json` for Claude Code and `.agents/hooks.json` for Antigravity; `.codex/hooks.json` invokes the same guard through `scripts/codex-campaign-hook.py`, and the OpenCode plugin `.opencode/plugins/rasterfold-campaign/index.js` through `scripts/opencode-campaign-hook.py` on each `session.execution.*` turn end (never on an interrupted turn); Muse has no Stop hook, so its runs rest on the guard file plus the heartbeat): while the run is open, it blocks the owning session's end of turn and names the next ready row. It lets the turn end when the guard file is gone, the run file has a `## Closeout run=<run id>` heading or a column-0 `PARKED <UTC> run=<run id>` line, or, for a plan-scoped run, `query ready` prints `0 runnable now`. A phase-scoped run (`--scope phase`, a standalone `process-phase`) ends only on its own marker and is never pointed at another phase's row, because `query ready` does not say which phase a row is in. It blocks only the session named in the guard file, never subagents or a second session, and it fails open on a bad payload, a thrown error, or its own 40-second budget running out inside the 60-second hook timeout. `python3 scripts/campaign_guard.py --self-test` drives it against a throwaway workspace inside `scripts/check-all.py`. It fails open, but a thrown error is recorded as `hook_error` in the state file, kept there through later hook runs until the heartbeat acknowledges it.
- **Stall breaker** (inside the hook): after 3 blocks in a row with no change to HEAD, the working-tree diff, the untracked files (content hashed for the first 500, size and write time for the next 5000, the name past that: an edit that keeps a file's size and time past the first 500 is invisible, and so is any edit past 5500), or the run file without its `- bookkeeping:` lines, the hook lets the turn end and counts a trip in `build/claude-campaign-state.json`. Real progress resets the count. A session that cannot move is stuck, and pushing it again only spends money. Bookkeeping is not progress: a heartbeat or retry note is written as a `- bookkeeping: ...` line and leaves the fingerprint unchanged, while any other Critical events line counts. The hook reads and writes its state under the same OS lock as `campaign_guard.py`, and a lock it cannot get fails open into one file per error under `build/claude-campaign-hook-errors/`.
- **Heartbeat** (`CronCreate` / `schedule` tool): it fires only when this session is idle, and it runs inside this session with full context, so it is a real resume, not a detached reminder. It covers the turns the hook cannot hold: a tripped breaker, an API error, a crash out of the turn. Every firing notes itself with `heartbeat-still`, so repeated resumptions with no tree change trip the same stall counter the hook feeds and a stuck run ends after two trips on every harness.

Start it in this order:

1. Reconcile first: `CronList` (`manage_task(Action="list")`), then `python3 scripts/campaign_guard.py reconcile --session $CLAUDE_CODE_SESSION_ID --jobs <every job id whose prompt contains run-guard heartbeat for RasterFold, comma-separated>`, and do what it prints: `CronDelete` (`manage_task(Action="kill", TaskId=...)`) an orphan or stale job, and start nothing when another session owns the guard. A crash between creating a job and acquiring a guard is repaired here, before a second one is made.
2. Mint a generation: `python3 scripts/campaign_guard.py mint-generation`. `CronCreate` with cron `3-59/5 * * * *`, recurring true, and the canonical prompt below with `<Writer>` (this harness: `Claude Code`, `Muse`, `Antigravity`, `Codex`, `OpenCode`, or `Copilot CLI`), `<N>`, `<run file>`, and `<generation>` filled in.
3. Acquire the guard: `python3 scripts/campaign_guard.py acquire --session $CLAUDE_CODE_SESSION_ID --phase <N> --run-file <run file> --cron-id <job id> --generation <generation> --scope plan` writes `build/claude-campaign-guard.json` (gitignored; `runner`, `workspace`, `phase`, the repo-relative `run_file`, `session_id`, `cron_id`, `scope` (`plan` when this skill starts the run, `phase` when a standalone `process-phase` does; every later re-point, job replacement, or handover leaves `--scope` out and so keeps the run's scope), `generation`, `job_created_at`, and `run_id`, the identity every terminal marker of this run carries, kept across re-points and handovers of the same run). It creates the guard exclusively and refuses one another session holds, so two sessions never share a run; the owning session re-points its own guard with the same command, and taking over another session's live guard needs the operator's `--handover <reason>`, recorded in the guard. Every guard change holds an interprocess lock, so no two changes interleave, and a fresh guard resets the breaker state under that lock. A refused `acquire` means another session owns the run: `CronDelete` the job step 2 just created, start nothing, and report the owner.
4. Record the session id, the job id, the generation, and the guard write in the run file's Critical events.

At every section boundary (after each stamp), check the heartbeat: `CronList`, then `python3 scripts/campaign_guard.py health --session $CLAUDE_CODE_SESSION_ID --jobs <live heartbeat job ids>` and `python3 scripts/campaign_guard.py expiry --session $CLAUDE_CODE_SESSION_ID`. A missing job, or one within 12 hours of its 7-day expiry, is replaced (steps 2 and 3 with a fresh generation and without `--scope`, so a standalone phase run stays phase-scoped) and the repair recorded in the run file.

The run file's end markers are exact and carry the run's id, the guard's `run_id` that `acquire` prints: a closeout is a line `## Closeout run=<run id>` followed by the closeout text, and a park is a column-0 line `PARKED <UTC stamp> run=<run id> <one-line reason>` followed by the park record, wherever in the file it sits. The hook, `end`, and the heartbeat honour only markers carrying this run's id, so a reused run file's old markers never end a new run however the file is edited; a guard written before run ids accepts any marker.

The heartbeat is session-only: it dies with this session, and a recurring job expires after 7 days, which the section-boundary `expiry` check replaces before it lapses. A run resumed in a new session takes the guard with `acquire --handover <reason>` and a new job and generation; the old session's heartbeat then reads `NOT THE OWNER` from `whoami` and deletes itself, and the hook never blocks the wrong session.

Every way a run ends (closeout, park, plan done, operator stop, escalation, a stall the heartbeat stops) deletes all three, always through the locked, session-checked `end` and never by deleting files directly: `python3 scripts/campaign_guard.py end --session $CLAUDE_CODE_SESSION_ID --reason <closeout|park|plan-done|operator-stop|escalation>` checks that path's marker (the `## Closeout` heading, the column-0 `PARKED` line, `0 runnable now`, nothing for a stop, a `PARKED ... escalation:` line), deletes the guard file and the state file, leaves `build/claude-campaign-pending-cancel.json` naming the heartbeat job, and names it; the runner `CronDelete`s it, confirms it gone with `CronList`, and only then runs `python3 scripts/campaign_guard.py cancel-confirmed --cron-id <job>`, so a failed delete stays recoverable.

Escalation ends the run before its report: a report to the operator (an exhausted repair bound, an unverifiable CI, a cause the tree cannot fix) first writes a column-0 `PARKED <UTC> run=<run id> escalation: <cause>` line, then runs `end --reason escalation` and deletes the job, so the Stop hook lets the report turn end and no heartbeat resumes against it. Resume recreates the guard and the job before any other step.

Operator stop: pressing Esc interrupts without the hook firing (`USER_CANCELED`). A stop or pause said in words deletes the guard file, the state file, and the job, in that order (`end --reason operator-stop`, then `CronDelete`), before confirming. Resume recreates all three before any other step.

Claude Code, Muse Code, Antigravity, Codex, OpenCode and Copilot CLI can write in this repository. Only one session may own a campaign guard at a time.

Canonical prompt:

```text
<Writer> run-guard heartbeat for RasterFold Phase <N> (run file <run file>, generation <generation>). This session went idle while a campaign run may still be open. Check, then act, in this turn.

1. Run `python3 scripts/campaign_guard.py whoami --session $CLAUDE_CODE_SESSION_ID --generation <generation>`. It prints OWNER with the run's id and scope (`OWNER run=<run id> scope=<plan|phase>`) when this job is the run's; the scope says what to resume in steps 5 and 7. If it prints NOT THE OWNER or NOT THE CURRENT JOB, this job is not the run's: CronDelete this job, read and change nothing else, and reply with that line. If it prints MALFORMED GUARD, run step 2, report the malformed guard to the operator, and stop.
2. Run `python3 scripts/campaign_guard.py hook-error --session $CLAUDE_CODE_SESSION_ID`. If it prints a line, the Stop hook failed open: append that line to <run file>'s Critical events, then run the same command with `--ack "<that line>"` to clear it.
3. Run `python3 scripts/campaign_guard.py pending-cancel`. If it names a job, CronDelete that job, confirm it gone with CronList, and run `python3 scripts/campaign_guard.py cancel-confirmed --cron-id <that job>`.
4. If step 1 printed NO GUARD, the run is over: run `python3 scripts/campaign_guard.py reset-state --expect-no-guard yes`, CronDelete this job (find it with CronList by this prompt's first sentence), and reply RUN FINISHED.
5. If <run file> has a line "## Closeout run=<run id>" or a column-0 line starting "PARKED" that carries "run=<run id>", with the run id step 1 printed, and step 1 printed scope=phase, the one phase asked for is over: run `python3 scripts/campaign_guard.py end --session $CLAUDE_CODE_SESSION_ID --reason closeout` (or `--reason park` for the PARKED line), CronDelete this job, confirm it gone with CronList, then run `cancel-confirmed` for it, and reply RUN FINISHED. With scope=plan, run `python3 scripts/todo-graph.py query ready`. If it prints `0 runnable now`, the plan run is over: run `python3 scripts/campaign_guard.py end --session $CLAUDE_CODE_SESSION_ID --reason plan-done`, CronDelete this job, confirm it gone with CronList, then run `cancel-confirmed` for it, and reply RUN FINISHED. Otherwise the phase ended but the plan did not: delete nothing, and resume under step 7, where process-plan re-points the guard to the next phase. A phase closeout alone never ends a plan run.
6. Run `python3 scripts/campaign_guard.py heartbeat-still --session $CLAUDE_CODE_SESSION_ID`. It notes this resumption against the run's progress: a changed tree resets the still count and the stall trips, and six resumptions in a row with no change count one trip (the same counter the Stop hook feeds, so harnesses with no hook still terminate). If build/claude-campaign-state.json then has trips of 2 or more: the run stalled twice with no change to the tree. Do not resume. Append a Critical events line to the run file naming what blocks it, run `python3 scripts/campaign_guard.py end --session $CLAUDE_CODE_SESSION_ID --reason stall`, CronDelete this job, confirm it gone with CronList, then run `cancel-confirmed` for it, and report the stall to the operator.
7. Otherwise append `- bookkeeping: heartbeat resumed <UTC>` to the run file's Critical events and resume: under process-phase for Phase <N> only when step 1 printed scope=phase, else the campaign under process-plan: re-run `python3 scripts/todo-graph.py query ready`, pick up the open section in the run file exactly where it stopped, and keep shipping: finish the section, stamp it, then the next section, then the next phase. A commit is not a stop, and a red CI is repaired, not waited on. Stop only at closeout, park, or an operator stop.
```

## 2. After a phase closeout or park

`process-phase` ends in exactly one of three ways: the phase table is all `[x]` and closeout is written; every leftover `[ ]` row is blocked or runnable-elsewhere in this context and it parked; or the operator paused it.

A parked phase is **not** complete, and it is **not** a stall. Do not call it either.

```bash
python3 scripts/todo-graph.py query ready
```

If another phase has a ready row, re-point the guard to the new phase's run file before anything else: `CronDelete` the old job, `CronCreate` a new one from the canonical prompt with the new phase and run file, re-point the guard with `python3 scripts/campaign_guard.py acquire` (`phase`, `run_file`, `cron_id`, a fresh `generation`, and `session_id` from this session) (a new run file resets the breaker state under the guard lock), and record the new ids in the new run file; then start `process-phase` on it in the same turn. Same session, same rules. If no phase has a ready row, the remaining leftovers are blocked, runnable-elsewhere in this context, or the plan is done: report which, with the budget line from `query budget` (sections, discovered sections, and backlog use). Commit the phase's run file at closeout or park at the latest (earlier ships allowed). When the plan is done (no `[ ]` rows anywhere), run the terminal acceptance before deleting the guard: re-execute the release domain's clean-machine acceptance section (the RasterFold `09-release` acceptance section for Windows/Linux binaries and libraries and both Android ABIs) fresh on a clean machine. A failure reopens that section through `review-todo-section` in audit stance and the plan is not done; a pass is recorded in the findings file, then the run ends through `python3 scripts/campaign_guard.py end --session $CLAUDE_CODE_SESSION_ID --reason plan-done`, which deletes the guard file and the state file under the guard lock, and the heartbeat job it names is `CronDelete`d. Until that section is authored, the plan cannot be declared done: file it through `add-todo` first. The acceptance row proves each target shippable when it ships; the re-run proves it still is when everything else has landed.

## 3. Deny

- Do not invent a side loop that ships rows outside `process-todo-section` plus `review-todo-section`.
- Do not start a second run, and do not start one while the current run is paused unless the operator said resume.
- Do not tick `implementation-plan.md` by hand.
- Do not claim a phase is complete while its table has `[ ]` rows.
- Do not treat a named phase as the whole plan. Chaining is this skill's job, and only this skill's.
- Do not end the turn on the audit table. Starting is the next action, in the same turn.
- Do not start a run without its guard file and heartbeat job, and do not end, stop, or pause a run without deleting both.
