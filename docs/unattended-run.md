# The unattended run

One double-click finishes RasterFold to 100%, in either of two runners: every open TODO section shipped, reviewed, and stamped, the terminal release acceptance re-run, and the plan closed. This file is the contract the launcher and the run both follow.

## How it starts

Two Windows Desktop shortcuts start it (operator directives 2026-11-12 and 2026-11-14): `RasterFold Claude campaign.lnk` runs `scripts/unattended-run.sh` (Claude Code) and `RasterFold Carbon campaign.lnk` runs `scripts/unattended-run.sh carbon` (Antigravity on `Orchestrator (Carbon)`, `--model gemini-pro-orchestrator`). Each opens Windows Terminal (the terminal Windows starts for `wsl.exe` when its default terminal is left to Windows, as on the operator's machine; with another default the same target line opens that terminal instead) into this WSL checkout and runs the launcher, which:

1. Takes the launch lock (`build/unattended-launch.lock`, held only for the preflight and released before Claude Code starts), so two double-clicks go through the preflight one at a time, then runs `python3 scripts/unattended-preflight.py --runner claude|gemini --repair --claim <session id> --claim-pid <launcher pid>`. Any FAIL stops the launch with the reason on screen (the terminal stays open). Nothing starts against a dirty tree, a stale plan, a missing reviewer, a dialog that would wait for a click, or a low disk. `--repair` rebuilds a stale compilation database (ignored build output, about 3 s a target) instead of refusing the start, and only after the branch, clean-tree, guard and launch-claim checks passed, holding the campaign guard's own lock and reading ownership again under it, so a second double-click during a live run rebuilds nothing under the running writer and no session can acquire the guard mid-rebuild. A repair that times out is killed with every process it started. When every check passes, the preflight records the launch in `build/unattended-launch.json` (the session id, and the launcher's pid, which `exec claude` or `exec agy` keeps).
2. Claude campaign: starts Claude Code straight on `main` (never a branch, never a worktree) with `--dangerously-skip-permissions --model opus --fallback-model sonnet --effort medium --session-id <fresh UUID> --disallowedTools AskUserQuestion,EnterPlanMode,ExitPlanMode --plugin-dir .claude/lsp/rasterfold-lsp`, seeded with the prompt below. `opus` is the alias for the latest Opus, so the launcher follows new Opus releases without an edit (operator directive 2026-11-12: Opus latest at medium, replacing the Fable launch of 2026-11-11).
3. Carbon campaign: starts Antigravity straight on `main` with `agy --dangerously-skip-permissions --model gemini-pro-orchestrator -i "<Carbon seed prompt> Launch id: <fresh UUID>."`. `gemini-pro-orchestrator` is Antigravity's `Orchestrator (Carbon)` model mode, which dynamically pairs Gemini 4 Carbon (planning, architecture, troubleshooting) with Gemini 4 Hydrogen (execution, edits, builds, test runs) inside one unified session and ships Antigravity's built-in read-only `research` subagent natively (operator directive 2026-11-14, replacing `gemini-4-carbon-medium` and the removed custom Hydrogen scout plugin). Antigravity takes no session id, so the UUID is a launch id carried at the end of the prompt, on `agy`'s command line, where the launch claim finds it; once the session acquires the guard with its Conversation ID, the preflight finds that owner by the conversation database (`~/.gemini/antigravity-cli/conversations/<id>.db`) `agy` holds open. The preflight's `--runner gemini` checks `agy` and `codex` on PATH, the Stop hook in `.agents/hooks.json`, and that no custom Antigravity subagents exist under `.agents/` instead of Claude Code's CLI, hook, dialogs, cron tools and language-server plugin. Antigravity has no flag that withholds a tool, so the seed prompt forbids questions and plan approval. Its work routes to GPT-6 Astra (`gemini = ["astra"]` in `.conclave/reviewers.toml`).

## Dry-launching without starting a campaign

`UNATTENDED_PROMPT_OVERRIDE=<file>` is the one documented dry-launch entry point: when the variable is set, `scripts/unattended-run.sh` reads the seed prompt from that file instead of the campaign prompt above (for Carbon, the launch id is still appended), so a dry launch can report its session id, model, and agent roster and end the turn without acquiring a campaign guard. When the variable is unset the launcher uses the campaign prompt exactly as written above, byte for byte. The preflight still runs first either way, so a dry launch on a tree the preflight refuses never reaches Claude Code.

## Why it actually runs unattended

- `--dangerously-skip-permissions` answers every permission check, so no tool call waits on a human. Its one-time acceptance dialog and the workspace trust dialog are the two things that could still sit unanswered at launch; the preflight checks that both were already accepted on this machine and refuses the start otherwise.
- `--disallowedTools AskUserQuestion,EnterPlanMode,ExitPlanMode` withholds the three tools that wait for a person: the question dialog and plan approval. The run cannot park on either. The AGENTS.md autonomy rule (operator directive 2026-11-10) covers the rest: decide and act, self-heal at the owning layer, improve tooling and plan as it goes, hold the best-in-class bar, and treat "impossible" as a claim needing measured proof in a section record.
- The goal is enforced, not hoped for. The campaign guard `Stop` hook (`python3 scripts/campaign_guard.py stop-hook`, wired in `.claude/settings.json`) blocks the owning session's end of turn and names the next ready row until `query ready` prints `0 runnable now`, a closeout, or a recorded park. Claude Code's own `/goal` command is deliberately not used: it is a second, model-judged stop condition whose evaluator cannot run tools, and at a legitimate park (every leftover row blocked or runnable-elsewhere) it would keep resuming a run the guard correctly ended.
- The in-session heartbeat from `process-plan` (`CronCreate`, `3-59/5 * * * *`) covers what the hook cannot hold: a stalled or crashed turn is resumed inside the same session with full context, and six resumptions with no tree change trip the stall breaker instead of burning tokens forever.
- A second launch always sees the first. `--session-id` puts the session's id on its command line, and the launch claim names that id and its pid from the moment the preflight passes, before the session has acquired any guard: a second launch finds the claim (or, later, the guard's owner in the process table) and is refused with `FAIL  no other unattended launch` or `FAIL  no live campaign guard`. An attended Claude Code session that owns a guard is found through Claude Code's session registry (`~/.claude/sessions/`); a registry that cannot be listed, or an entry that cannot be read for a live process, is treated as a possible owner, never as a dead one.
- Reviews never wait on the operator: `scripts/review-dispatch.py` runs the pinned reviewer (`claude` routes to GPT-6 Astra through the Codex CLI) through plan, adversarial round, completion, and reconciliations up to the 33-pass cap per section, each on the whole template as `scripts/review-prompt.py` fills it.
- Every commit passes the local hooks (staged-tree TODO validate, plan audit, drift) with no `--no-verify`, straight on `main`, one section per logical candidate range, pushed in the same turn.

## Read-only Sonnet scouts, Orchestrator (Carbon), and how quality is kept

In Claude Code, the lead makes every edit and runs every command, and the only custom agents in the repository are three Claude Code subagents in `.claude/agents/`, each on Sonnet with the tool list `Read, Grep, Glob` (operator directive 2026-11-11: read-only Sonnet agents for near-mechanical work). In Antigravity, `Orchestrator (Carbon)` (`--model gemini-pro-orchestrator`) handles Carbon/Hydrogen execution handoffs and Antigravity's built-in read-only `research` subagent natively inside the session, so no custom Antigravity subagent plugin or wrapper exists (operator directive 2026-11-14, removing the custom Hydrogen scouts added on 2026-11-12):

| Claude Code scout | Takes off the lead | Returns |
| ----- | ------------------ | ------- |
| `rf-scout` | Finding where a symbol, constant, section, claim, or string lives, and counting its uses | `path:line` with the line quoted |
| `rf-log-digest` | Reading a long log or gate output that already exists | Failing lines, count lines, last lines, quoted |
| `rf-fact-check` | Comparing the paths, counts, line references, and cross-references a TODO section states with the tree | Each mismatch with both sides quoted |

Read-only for the Claude scouts is a property of the tool list, not of the prompt: a scout has no tool that edits, writes, or runs a command, and the preflight refuses if any `.claude/agents/` file names another model, another tool, or a frontmatter key that could add one (`roster_problems()` in `scripts/unattended-preflight.py`), while `antigravity_custom_agent_problems()` ensures no custom Antigravity subagents exist under `.agents/`. This is what separates the setup from the worker tiers removed on 2026-11-10, which wrote files and interpreted instead of escalating.

Shipped quality stays where it was (operator instruction 2026-11-11), by these rules, which `AGENTS.md` carries as the working rule:

- A Claude scout or built-in `research` subagent returns quoted evidence, never a verdict. The session never adopts a subagent's conclusion unread.
- Every fact a decision, an edit, or a recorded claim rests on is re-checked against source with one command or one read of the quoted line before it is used.
- For Claude scouts, a new class of work is replayed once on a known-answer input before it is delegated, and one wrong, invented, or unquoted answer removes that scout for the rest of the run, recorded in the run file, with its work redone by the lead.
- No session spawns writing subagents or `/swarm` branch/worktree workers (writes stay serial straight on `main`), and judgment, codec and format work, gate verdicts, reviews, stamps, and commits never delegate.
- Nothing a subagent says replaces a gate, a checkpoint, or the pinned three-pass independent review. Those decide what ships, and they are unchanged.

Honest limit: a scout can still miss something that is there. That is why its output is only ever a pointer for the lead to check, and why a miss costs a second look rather than a wrong commit. Reversal cost: delete `.claude/agents/` and `roster_problems()` to make Claude Code lead-only, or restore the removed Antigravity scout files from git history if custom Antigravity scouts are ever wanted again.

## Language servers for the writer

`--plugin-dir .claude/lsp/rasterfold-lsp` gives the session clangd (the pinned `tools/llvm-mingw-linux/bin/clangd`, reading the root `compile_commands.json`) for `.c` and `.h`, and Basedpyright (`.venv/bin/basedpyright-langserver`) for `.py`: definitions, references, hover, and diagnostics after each edit, from the same binaries the editors use. An attended session gets the same with `claude --plugin-dir .claude/lsp/rasterfold-lsp` (`docs/building.md`, Editor setup).

## Stopping and resuming

- Operator stop in words: `python3 scripts/campaign_guard.py end --reason operator-stop`, delete the heartbeat job, done (process-plan spells the order). Pressing Esc interrupts a turn without the hook firing.
- Resume: double-click either shortcut again (a run started in one runner can be resumed in the other through the same guard handover). Preflight refuses while a guard from a live run exists (its named session is still running, or might be). A dead run's guard does not stop the launch: the preflight prints `stale campaign guard: <session> (handover on start)` and passes that line, and the new session takes the guard over, never by deleting files, in this order: `CronList` and delete any heartbeat job still live for the dead run, create the fresh heartbeat job and mint a generation as `process-plan` spells, then `python3 scripts/campaign_guard.py acquire --session <new session> --phase <N> --run-file <run file> --cron-id <new job> --generation <generation> --handover <reason>` and read the handover back from the guard it prints. A heartbeat from the dead session dies with that session, so any job `CronList` still shows for it is stale and is deleted before the new job is created.

## The Desktop shortcuts

`scripts/install-launchers.ps1`, run once on Windows from this checkout (`pwsh -File \\wsl.localhost\Ubuntu\home\<user>\projects\RasterFold\scripts\install-launchers.ps1`), writes both shortcuts and their icons and removes the old `RasterFold Unattended Run.lnk`. Each icon is the RasterFold mark (`assets/brand/icon.svg`) with its runner's badge in the corner, as the Isotone campaign shortcuts carry theirs: a terracotta circle with the Claude symbol for Claude, a blue circle with the Gemini sparkle for Carbon, both with a white outline and a white mark from 32 pixels up. The icons are rendered per machine to `%LOCALAPPDATA%\RasterFold\` with `resvg-py` and Pillow in the Windows Python (the pair Isotone's `scripts/requirements-icons.txt` pins); they are local launcher icons only and ship in nothing, so neither package becomes a dependency of the codec, its tests or its tooling.
